# ArchiMate (PlantUML Standard Library) Reference

The ArchiMate PlantUML standard library adds typed enterprise-architecture elements and relationships to PlantUML. Use it for ArchiMate layer views (Motivation, Strategy, Business, Application, Technology, Physical, Implementation) generated by `/arckit:archimate`.

**Stdlib**: [plantuml-stdlib `stdlib/archimate/Archimate.puml`](https://github.com/plantuml/plantuml-stdlib/blob/master/stdlib/archimate/Archimate.puml) (ArchiMate 3 macros, stdlib version 3.2.2)

**Fixture**: `tests/fixtures/archimate/three-layer.puml` (rendered SVG committed alongside) is the render-truth reference — re-run it when pinning a new PlantUML version.

---

## Pinned API

Pinned **2026-09-13** against **PlantUML 1.2026.8** (Java 21, `plantuml-1.2026.8.jar`). Any change to this section requires re-rendering the fixture and a new pin date.

### Pinned include line

```plantuml
!include <archimate/Archimate>
```

- Native angle-bracket include — resolved from the PlantUML jar's embedded standard library (bundled since **V1.2017.14**).
- URL-based rendering environments: `!include https://raw.githubusercontent.com/plantuml/plantuml-stdlib/master/stdlib/archimate/Archimate.puml` (works where URL includes are enabled; do **not** inline the stdlib source into public-URL diagram text — a full inline adds ~3.6 KB to the encoded URL and the macros must be re-fetched per render).
- Minimum supported version: **1.2025.8** (SVG sprites, stdlib 3.2.x line). Hard floor: 1.2017.14 (stdlib introduced) — older jars render with stale PNG sprites and a superseded macro set; bump the jar instead of forking the macros.

### Relationship surface — `Rel_<Type>(from, to, "label")`

Base types: `Access` (variants `Rel_Access_r`, `Rel_Access_rw`, `Rel_Access_w`), `Aggregation`, `Assignment`, `Association` (variant `Rel_Association_dir`), `Composition`, `Flow`, `Influence`, `Realization`, `Serving`, `Specialization`, `Triggering`.

- Every type supports an optional direction suffix: `Rel_<Type>_Up|_Down|_Left|_Right`.
- Directional variants of `Access` and `Association` inherit the same suffixes.

### Layout helpers & boundaries

| Macro | Effect |
| --- | --- |
| `LAYOUT_TOP_DOWN()` | `top to bottom direction` |
| `LAYOUT_LEFT_RIGHT()` | `left to right direction` |
| `LAYOUT_AS_SKETCH()` | handwritten-style "unvalidated" layout |
| `Lay_U/D/L/R(e1, e2)` | hidden placement edges (no arrowhead) |
| `Boundary(alias, "label")` | labelled boundary rectangle |
| `Group` / `Grouping` | grouping containers |
| `Junction_And` / `Junction_Or` | AND/OR junction circles |

### Colour standards

Per-layer fills are PlantUML **named-colour tokens** (`#Business`, `#Application`, `#Technology`, …) from the theme layer. Standard theme (`<archimate/themes/puml-theme-archimate-standard>` — the default when no theme is set) fills measured in the 1.2026.8 fixture render:

| Layer | Token | Rendered fill (1.2026.8) |
| --- | --- | --- |
| Business | `#Business` | `#FFFFCC` |
| Application | `#Application` | `#C2F0FF` |
| Technology | `#Technology` | `#C9FFC9` |

(Values read from the committed fixture render `tests/fixtures/archimate/three-layer.svg`: `bProcess` → `#FFFFCC`, `aComp`/`aData` → `#C2F0FF`, `tNode` → `#C9FFC9`. Re-verify against the fixture whenever the pin is re-rendered.)

Do not hard-code hex layer colours in generated diagrams — use the tokens so theme swaps (saturated / low-saturation / handwriting) stay automatic.

### Public-URL length behaviour

Measured with the jar's own `Sv`+deflate encoding (2026-09-13):

| Source | Encoded public URL |
| --- | --- |
| 481 B four-element fixture | 419 chars |
| Full 23 KB stdlib **inlined** | 3,831 chars |

Unique ArchiMate content compresses to roughly 10–20 URL chars per element; a 100-element view stays under ~3 KB. The public-URL path is therefore viable for views, *provided* the rendering server has the stdlib embedded — never inline the stdlib into the diagram source.

### Notation decision

**Native ArchiMate stdlib macros are the pinned notation** (recorded 2026-09-13, task 0.4). Rationale: the stdlib provides typed, directional ArchiMate relationship macros (`Realization`, `Serving`, `Access` — exactly the edge types the ArchiMate quality gate requires), per-layer element macros with correct sprites, and versioned stdlib evolution (3.2.2). No C4-PlantUML fallback was needed: C4-PlantUML has no ArchiMate relationship vocabulary.

Fallbacks (documented, not used today):

1. **C4-PlantUML with ArchiMate-flavoured stereotypes** — only if a rendering target predates the ArchiMate stdlib (pre-1.2017.14) or URL-include restrictions block both include forms.
2. **Raw `archimate` keyword** (`archimate #Technology "VPN" as vpn <<technology-device>>`) — escape hatch for ad-hoc single elements where a typed relationship is not needed.

## Notation Cheat-Sheet

Minimal complete example (mirror of `tests/fixtures/archimate/three-layer.puml`):

```plantuml
@startuml
title ArchiMate three-layer sample (ArcKit fixture)
!include <archimate/Archimate>

LAYOUT_TOP_DOWN()

Business_Process(bProcess, "Claims intake process")
Application_Component(aComp, "Claims administration component")
Application_DataObject(aData, "Claims record (logical data object)")
Technology_Node(tNode, "Claims platform node")

Rel_Realization(aComp, bProcess, "realizes")
Rel_Flow(bProcess, aData, "produces")
Rel_Access_rw(aData, tNode, "reads/writes")
@enduml
```

Quick syntax map:

| Intent | Syntax |
| --- | --- |
| Declare a typed element | `Category_ElementName(alias, "description")` |
| Typed relationship with label | `Rel_<Type>(from, to, "label")` |
| Directional hint | `Rel_<Type>_Up\|_Down\|_Left\|_Right(from, to, "label")` |
| Read / read-write / write access | `Rel_Access_r` / `Rel_Access_rw` / `Rel_Access_w` |
| Top-down layer stack | `LAYOUT_TOP_DOWN()` (or `LAYOUT_LEFT_RIGHT()`) |
| Hidden placement edge | `Lay_D(from, to)` / `Lay_U` / `Lay_L` / `Lay_R` |
| Labelled boundary container | `Boundary(alias, "label")` |
| AND/OR junction | `Junction_And` / `Junction_Or` |
| Custom notation legend | `legend ... end legend` block |
| Colour an element by layer | `#Business`, `#Application`, `#Technology` tokens (theme-provided) |

Aliases must be declared before any relationship references them; relationships always take a label as the third argument.

## Layer-Tier Ordering Rules

The ArchiMate layer stack, top (most abstract) to bottom (most concrete):

1. Motivation (drivers, goals, outcomes, requirements, constraints)
2. Strategy (capabilities, value streams, courses of action, resources)
3. Business (processes, services, events, objects, roles)
4. Application (components, services, data objects, interfaces)
5. Technology (nodes, system software, devices, artifacts)
6. Physical (facilities, equipment, distribution)
7. Implementation (plateaus, work packages, gaps)

In a generated view:

- One structural layer per view, plus an optional Motivation (or Strategy) overlay.
- `LAYOUT_TOP_DOWN()` with declarations in tier order: overlay elements first, then the structural layer top-to-bottom within that layer.
- Edges connect **adjacent tiers only** (overlay → layer, layer → layer). A two-tier jump (e.g. Business → Technology) must never be drawn: insert the intermediate element, or split the view.
- Use `Lay_D`/`Lay_U` hidden edges for placement only — never to carry semantics.

## Realization / Relationship Direction Rules

- **`Rel_Realization` always points concrete → abstract**: `Application_Component` → `Business_Service`/`Business_Process`, `Technology_Node` → `Application_Component`/`Application_Service`, `Strategy_Capability` → `Business_Process`/`Application_Service`. A flipped edge ("abstract realizes concrete") is a quality-gate FAIL (criterion 2).
- **`Rel_Serving`** points service → provider component: `Application_Service` → `Application_Component` ("serves"), `Business_Service` → `Business_Process` where the service fronts the process.
- **`Rel_Flow`** attaches the producing/consuming element to the data object; label the verb ("produces", "consumes") so direction is readable.
- **`Rel_Access_r|_rw|_w`** points the accessing element → the object/node it accesses; pick the variant that matches the access mode, never the plain `Rel_Access` when the mode is known.
- **`Rel_Influence`** is the Motivation→structural connector (driver/constraint/goal → capability or process), not to be confused with `Rel_Realization`.
- Every edge carries a one-line label; unlabelled edges fail quality-gate criterion 4.

## Capability-Map ArchiMate Nesting

A hierarchical capability map (L1 domains → L2 sub-capabilities → optional L3
detailed capabilities) is an ArchiMate-representable Strategy-tier view:

- Each node is a `Strategy_Capability` element; nesting depth is L1 → L2 → (optional L3).
- Whole→part edges use `Rel_Composition(parent, child, "contains")` (default) or `Rel_Aggregation` where a sub-capability clearly retains standalone existence. Point them L1→L2 whole→part — **never** reversed.
- Composition edges are **not** realization edges: the concrete→abstract `Rel_Realization` rule does not apply to `Rel_Composition` / `Rel_Aggregation`; the "whole" (parent domain) connects down to the "part" (child sub-capability).
- `LAYOUT_TOP_DOWN()`; keep the hierarchy top-down so parent domains read above their children.
- The ≤ 12 elements/layer gate still applies to the combined L1+L2 view; above the gate, split at a natural capability-domain boundary into additional sequenced `ARCH` documents (cross-linked in Linked Artifacts) — never silently drop.

```plantuml
@startuml
!include <archimate/Archimate>
LAYOUT_TOP_DOWN()
Strategy_Capability(P, "Policy & Underwriting")
Strategy_Capability(P1, "Decisioning")
Strategy_Capability(P2, "Policy Admin")
Rel_Composition(P, P1, "contains")
Rel_Composition(P, P2, "contains")
@enduml
```

## Capability-Map Complexity-Adaptive Rendering (top-down, by refinement level)

Build every capability-map diagram **top-down** (`LAYOUT_TOP_DOWN()`; a parent
always reads above its children). Choose the *set* of diagrams from model
complexity (total elements `E` across all present levels + widest single level):

- **Simple (`E ≤ 12`) → one flattened diagram:** a single top-down view of every
  present level (L1 → L2 → optional L3).
- **Complex (`E > 12`, or a single level denser than ~12) → abstract level-by-level,
  one diagram per refinement:**
  1. an **abstract overview** — top level only (L1 domains, each labelled with its
     child count as a roll-up);
  2. **refinement** diagrams, one **per L1 domain** (that domain's L2 sub-hierarchy +
     L3 when defined). Each refinement is a separate sequenced `ARCH` document,
     gated to ≤ 12 elements/layer; refine further per sub-domain if still dense —
     never silently drop. Cross-link abstract ↔ refinement.

```plantuml
@startuml
!include <archimate/Archimate>
LAYOUT_TOP_DOWN()
' abstract overview: L1 domains with a child-count roll-up
Strategy_Capability(D1, "Policy & Underwriting (4 sub-caps)")
Strategy_Capability(D2, "Channel & Distribution (3 sub-caps)")
@enduml
```

## Colour Standards

Use the theme's named colour tokens (`#Business`, `#Application`, `#Technology`, …) — **never hard-code hex layer colours** (see the rendered-fill table in § Pinned API for what each token produces on 1.2026.8). Theme swaps (saturated / low-saturation / handwriting) stay automatic only when tokens are used. Any notation beyond the stdlib vocabulary (custom stereotypes, hand-drawn shapes) must be documented in a `legend` block in the same diagram (quality-gate criterion 8).

## Element-Count Threshold

**Maximum 12 elements per layer.** Above 12, split the view at a natural architectural boundary (process group, capability, or subsystem) and emit additional sequenced `ARCH` documents, cross-linked in Linked Artifacts — never a crowded kitchen-sink diagram. The 12-element budget counts structural elements of the view's layer; overlay Motivation elements are tracked separately but should stay ≤ 6 (drivers, goals, constraints) before the view is split.

## Antipatterns (never emit)

| Antipattern | Why it fails | Fix |
| --- | --- | --- |
| Cross-layer noise: a Business element connected directly to a Technology element | Two-tier jump; hides the realizing application element | Insert the intermediate element or split into two views |
| Unlabelled relationship edges | Reader cannot distinguish "realizes" from "reads" | Add a one-line label to every `Rel_*` call |
| Mixing C4-PlantUML elements (`Person`, `System`, `Container`) or raw UML boxes into an ArchiMate view | Notation purity (criterion 5); C4 macros and ArchiMate macros have colliding relationship semantics | Express the same content with the layer's ArchiMate macros; keep C4 in its own `/arckit:diagram` artefact |
| Hard-coded hex layer colours | Breaks theme swaps; drifts from the pinned colour standard | Use `#Business`/`#Application`/`#Technology` tokens |
| Kitchen-sink view: more than one structural layer, or > 12 elements per layer | Unreadable; defeats the one-view-per-layer governance model | Split at natural boundaries; sequence the views |
| Inlining the stdlib source into public-URL diagram text | ~3.6 KB URL bloat; macros re-fetched per render | Use the pinned `!include <archimate/Archimate>` line (or the raw-URL include form) |

## Diagram Production Policy

When a document-generating command needs a diagram, decide whether to render it with the ArchiMate stdlib:

1. **Use PlantUML ArchiMate** when a diagram is *ArchiMate-representable* — i.e. it depicts an architecture concern this notation models: a layer or tier (Motivation / Strategy / Business / Application / Technology / Physical / Implementation), capabilities, services, application or technology components, or motivation (drivers, goals, outcomes, constraints). Also use it when an *additional* ArchiMate view should be added to a document even if the document already carries other diagram types.
2. **Representable vs not (heuristic).** Yes → layer/tier, capability, service, application/technology component, motivation (driver/goal/outcome/constraint), value stream, course of action. No → sequence / call interaction, entity–relationship (ER), Gantt / schedule, timeline / roadmap, or data-flow that carries no architectural typing. For the "No" cases, keep the document's existing diagram mechanism (e.g. Mermaid) — this policy does not force ArchiMate where the content is not an architecture view.
3. **Inline source, SVG-only output.** When this policy applies, carry the PlantUML ArchiMate source *inline* in the document and render it to a **self-contained `.svg`** (see § Offline Self-Contained SVG Rendering). The `.svg` is the **only new file emitted** — do not create new architecture document files (no new `.md` or `.puml` artefacts) to host the diagram or its source.

## Offline Self-Contained SVG Rendering

ArchiMate `.svg` deliverables are produced offline against the **pinned build** already declared in § Pinned API — PlantUML **1.2026.8**, Java 21, `plantuml-1.2026.8.jar`. Render with the jar directly (no public server, no URL-include path):

```sh
java -jar plantuml-1.2026.8.jar -tsvg -checkonly some-view.puml   # validate
java -jar plantuml-1.2026.8.jar -tsvg some-view.puml               # emit some-view.svg
```

Because the pinned jar embeds the ArchiMate stdlib, `!include <archimate/Archimate>` resolves offline — no fetch at render time.

**Self-containment expectation (verify before delivery):** an emitted ArchiMate `.svg` SHALL contain **no `http(s)://` URL other than the W3C XML namespace declarations** (`http://www.w3.org/2000/svg`, `http://www.w3.org/1999/xlink`), and all `xlink:href` values limited to **local `#anchors`**. It must open and render fully offline (no external assets, fonts, or scripts). Quick check:

```sh
grep -rhoE "https?://[^\"' )]+" some-view.svg | sort -u   # expect only the two W3C namespaces above
```

## BMM Projection

The pinned stdlib is 3.x-flavoured. BMM 1.3 (ArchiMate 4.0-aligned) adds three Motivation/Strategy elements with **no native macro** in the pinned library: **Objective**, **Measure**, and **Strategic Theme**. They are encoded as stereotypes — never faked as native. Full BMM fidelity (case narrative, assumption rationale, impact-factor analysis) lives in the BMM markdown artefact (`/arckit:bmm`, `ARC-{P}-BMM-v1.0.md`); views are *projections* of that model, not a substitute for it.

### Stereotyped encodings

| BMM element | Encoding |
| --- | --- |
| Objective | `Motivation_Goal(alias, "Objective: …")` |
| Measure | `Motivation_Goal(alias, "Measure: …")` |
| Strategic Theme | `Strategy_Capability(alias, "Theme: …")` or a `group` container |

- **Single-tier stereotyping:** one view carries stereotypes from either the Motivation tier (Objective / Measure) or the Strategy tier (Theme) — never both.
- **Legend is mandatory:** every view using a stereotype carries a `legend` block mapping the encoding to its plain-English meaning. Where no native macro exists for a relationship (e.g. "contributes to"), the edge style is defined in that same `legend` block — never invent notation without documenting it.

### Relationship vocabulary (BMM → pinned macros)

| BMM relationship | Encoding |
| --- | --- |
| instruments / influences | `Rel_Influence` (labelled "drives" / "constrains" / "expects" / "values") |
| realizes | `Rel_Realization` — always **concrete → abstract** (goal → outcome, objective → goal, capability → process) |
| contributes to | `Rel_Influence` or a legend-defined edge (no native macro) |
| contains / part of | `Rel_Composition` (whole → part, the BPCM idiom) / `Rel_Aggregation` |
| measures | `Rel_Realization` (labelled "measures") |
| assigned to | `Rel_Assignment` (resource → course of action) |
| outcome stream (optional) | `Rel_Flow` |
