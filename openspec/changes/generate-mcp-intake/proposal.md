## Why

The arckit-mcp relay server currently synthesizes placeholder intake questions
(`server.py` `_intake_questions()`, L313) — one generic question per doc-type
code — because it has no machine-readable source of the real intake questions.
The proposal to generate an `intake.py` from `intake-instructions.md` is
unsound as stated: that file is the interview **algorithm** (resolve effective
template → derive inputs), and contains zero per-command questions. A generator
parsing only that file would emit an empty `INTAKE` dict.

Verified source-of-truth map:

- Concrete question lists live in **29 question-block templates in the flat
  tree** (`plugins/{arckit-togaf-adm,it4it,oaa,agent-architecture}/templates/`).
  The nested tree (`plugins/arckit-claude/plugins/{arckit-it4it,oaa}/templates/`)
  holds **11 byte-near-identical duplicates** (it4it × 6 + oaa × 5), where the
  oaa `agile-strategy-template.md` pair differs only in one command-namespace
  string. The generator must dedup (rule in design.md §2) and the
  byte-stability test pins that.
- **The core plugin `arckit-claude` (78 commands, what the MCP server relays)
  has zero templates with question blocks.** Its 63 commands reference
  `intake-instructions.md`, the algorithm, not a question list.
- Explicit question coverage exists only in framework/overlay plugins:
  `togaf-adm` (12/12), `it4it` (6/6), `oaa` (5/5),
  `agent-architecture` (6/6).
- MANDATORY prerequisite tiers live in `GATE_TIERS` (generated by
  `generate-mcp-gates.py` from `**MANDATORY**` tier headers in command
  markdown).

So the upgrade is: parse **template question blocks + MANDATORY prerequisites**,
key the result by **template/doc-type** (not by command), accept that the core
plugin contributes almost nothing static, and keep persistence on the agent side.

## What Changes

- **New generator `scripts/generate-mcp-intake.py`** (arc-kit): scans the
  question-block-bearing templates in `plugins/*/templates/` (and
  `plugins/arckit-claude/plugins/*/templates/`), extracts each
  `## Intake Interview Questions` block, and emits `arckit-mcp/arckit_mcp/intake.py`
  containing:
  - `INTAKE: dict` keyed by **doc-type code**, value shape
    `{"questions": [str, …], "mandatory_inputs": [str, …],
    "source": "<template-path>"}` — `questions` is the union of the template's
    question block and the MANDATORY prerequisite input prompts (from the
    `**MANDATORY**` tier headers `generate-mcp-gates.py` already parses), and
    `mandatory_inputs` records which inputs are structural (block when
    missing).
  - A `COVERAGE` report section flagging doc-types with no static questions
    (i.e. the core-plugin gap), so an empty/near-empty emit for
    `arckit-claude` is *loud*, not silent.
  - The standard generated-file header ("Generated by
    scripts/generate-mcp-intake.py — DO NOT EDIT BY HAND"), the
    `ARCKIT_MCP_ROOT` / CLI-arg output-path convention from
    `generate-mcp-registry.py`, and pure regex/Python parsing (no node in CI).
- **New `arckit_mcp/intake.py`** (arckit-mcp, generated): the data artifact
  consumed by the server.
- **`arckit_mcp/server.py`** changes:
  - `_intake_questions()` (L313): replace the synthetic per-doc-type placeholder
    loop with a lookup into `intake.INTAKE`; **fall back to the current
    placeholder** when a doc-type has no static entry (the core-plugin case),
    so behavior degrades gracefully rather than returning nothing.
  - `run_command()` (L412): return the derived intake entries in the response
    payload; fold an **intake-completeness** check into the existing
    `check_gates` calls (L423–424).
  - **Intake-completeness gate is soft/structural only**: skipped answers
    render as `TBD` and never block; only *structurally missing* MANDATORY
    prerequisite inputs block. Bulk `arckit-build` mode must remain
    non-interactive, reading saved `.arckit/intake/` answers, and must not trip
    the soft gate.
  - **New tool `arckit.persist_intake`** (registered near `arckit.persist_artifact`,
    L477): a **read/seed** tool for bulk-build mode — loads saved
    `.arckit/intake/` answers to prefill a bulk run. It is **not** the write
    path: Agent A (the interview owner) remains the sole persister, preserving
    the relay constraint that the server never proxies user I/O.
- **Tests**:
  - `tests/mcp/test_intake.py` (arckit-mcp): round-trip — generated `INTAKE`
    dict → `run_command` intake payload → soft-gate behavior (`TBD` never
    blocks; structural MANDATORY miss does).
  - Generator round-trip test in arc-kit: emitted `intake.py` is byte-stable
    on re-run, and the COVERAGE warning fires for doc-types with no question
    block.

## Non-Goals

- No change to `intake-instructions.md` or to Agent A's interview behavior —
  the LLM-side algorithm stays as is; the generated file *augments*, not
  replaces, it.
- No write-path persistence in the server (Agent A owns persistence).
- No per-command keying: the data varies by *effective template* (user
  overrides via `.arckit/templates-custom/` are invisible to static generation),
  so keying by command would be wrong.
- No expectation of static coverage for `arckit-claude` core commands — the
  COVERAGE report documents the gap; those commands keep placeholder fallback.

## Compatibility

- Additive in arckit-mcp: new module + new tool + richer `run_command` payload.
  Existing consumers see the same shape plus more real questions where
  coverage exists.
- The fallback keeps every doc-type returning *something* (placeholder or
  derived), so no consumer regression.
- Bulk build: unaffected — soft gate + seed path preserve non-interactive
  behavior.

## Impact

- Affected specs: new capability `mcp-intake` (the delta in
  `specs/mcp-intake/` in this change). No spec exists in arc-kit for the
  generator itself (it follows the established `generate-mcp-*.py` pattern);
  the arc-kit side is a tooling change, spec'd here by this change only.
- Two-repo delivery: arc-kit ships the generator; arckit-mcp ships
  `intake.py` + server.py + tests. `intake.py` is regenerated by pointing
  `ARCKIT_MCP_ROOT` at the sibling checkout, exactly as
  `generate-mcp-registry.py` does today.
