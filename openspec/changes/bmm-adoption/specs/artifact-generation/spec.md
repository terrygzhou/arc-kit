# artifact-generation Delta — bmm-adoption

## ADDED Requirements

### Requirement: BMM Artefact Registration (BMM)
The system SHALL register the doc-type code `BMM` (name
`Business Motivation Model`, category `Planning`) in
`config/doc-types.mjs` `DOC_TYPES` AND in the `/arckit:pages`
known-artifact-types table, satisfying the dual-registration guard
(`scripts/check-doc-type-registry.py`). `BMM` SHALL be
**single-instance**: it MUST NOT appear in `MULTI_INSTANCE_TYPES` or
`SUBDIR_MAP`, so the artefact is the root-level
`ARC-NNN-BMM-v1.0.md` (one BMM model per project, versioned by
`-vN.N`, not sequenced with `-NNN-`). Generation SHALL be
template-driven from `templates/bmm-template.md` (custom override
`.arckit/templates/bmm-template.md` first, per the template-driven
generation contract), and the template SHALL carry the canonical
14-field Document Control table and generation footer so rendered
`ARC-*-BMM-*.md` artefacts pass checklist common checks #1 and #7.

#### Scenario: BMM write is single-instance at project root
- **WHEN** a write targets `projects/001-*/ARC-001-BMM-v1.0.md`
- **THEN** `validate-arc-filename.mjs` accepts the root-level
  single-instance name (no `-NNN-` sequence, no subdirectory), and a
  second run writes `ARC-001-BMM-v2.0.md` instead of a new sequence

#### Scenario: BMM code is registered in both halves
- **WHEN** `scripts/check-doc-type-registry.py` runs after this
  change
- **THEN** `BMM` is present in `DOC_TYPES` and the pages
  known-artifact-types table, and absent from `MULTI_INSTANCE_TYPES`
  / `SUBDIR_MAP` — no parity or multi-instance parity error

#### Scenario: BMM template renders a conforming Document Control
- **WHEN** an artefact is generated from `bmm-template.md`
- **THEN** its Document Control table lists all 14 canonical fields
  (placeholders permitted) and its generation footer carries
  Generated by, Generated on, ArcKit Version, Project, and Model

### Requirement: BMM Artefact Pipeline
The BMM generation pipeline SHALL run the stages in
`design.md` § Artefact Pipeline in order, and SHALL satisfy these
invariants:

1. **Inputs**: STKE + PRIN are mandatory (stop-and-ask if missing);
   SOBC/ROAD/WARD/RISK are recommended (read if present, note if
   missing); external strategy documents from `external/` are cited
   per `references/citation-instructions.md`.
2. **Stage 1 [A1]**: the BMM model artefact
   (`ARC-{P}-BMM-v1.0.md`) carries all nine pipeline sections —
   (1) stakeholders & outcomes incl. stakeholder–outcome matrix,
   (2) outcomes → goals → objectives → measures ladder, (3)
   drivers, (4) assumptions, (5) case for / case against, (6)
   impact factors, (7) strategic themes → capabilities → courses
   of action → resources, (8) traceability + external references,
   (9) Mermaid mindmap companion — plus Document Control +
   generation footer.
3. **Stage 2**: the base views [A2] Motivation and [A3]
   Strategy/Capability are ALWAYS emitted as sequenced `diagrams/`
   `ARCH` documents (skipped only when Q1 selects a model scope
   that omits the corresponding tier), each with a self-contained
   `.svg` render (pinned jar, offline, no non-local URLs).
4. **Stage 3**: the companion menu ([O1] goal–objective–measure
   ladder, [O2] case & assumptions overlay, [O3] alignment /
   traceability view, [O4] Mermaid mindmap sidecar) is
   user-selected at intake; each companion is its own sequenced
   `ARCH` document or an in-artefact block, never merged into a
   base view.
5. **Sequencing**: BMM-emitted views take the next free number in
   the shared `ARCH` sequence space; existing `ARCH` documents are
   never renumbered or rewritten.
6. **Additivity**: all edits to pre-existing commands, templates,
   and Mermaid blocks are append-only and byte-preserving
   (SHA-256 fixture extended, per the archimate-demanded-artefacts
   pattern); `extensions/*` are regenerated, never hand-edited.
7. **Gates**: G1–G5 (ladder completeness; no empty Case/
   Assumption/Impact-Factor quadrants; every strategic theme
   realizes ≥ 1 capability; view conformance — pinned include,
   ≤ 12 elements/layer, split-never-drop, realization concrete →
   abstract, legend for custom notation; ARCH sequence
   continuity) are evaluated with the 3-iteration remediation loop
   before [A1] is written.

#### Scenario: a full-scope run produces the complete pipeline set
- **WHEN** `/arckit:bmm` runs with full-model scope, all four
  companions selected, and the project's next free ARCH sequence is
  3
- **THEN** the run writes `ARC-001-BMM-v1.0.md` plus five ARCH
  documents at sequences 3–7 ([A2], [A3], [O1], [O2], [O3]) with
  self-contained `.svg` renders, and [O4] appended to [A1] as an
  in-artefact Mermaid block

#### Scenario: BMM views never renumber existing ARCH documents
- **WHEN** a project already carries `ARC-001-ARCH-001-v1.0.md`
  and `ARC-001-ARCH-002-v1.0.md` and `/arckit:bmm` emits its two
  base views
- **THEN** they land at sequences 003 and 004 and sequences 001–002
  are byte-identical to before the run

#### Scenario: gate failure blocks the write
- **WHEN** the generated model violates G1–G3 after 3 remediation
  iterations
- **THEN** [A1] is not written silently: the artefact (or the view,
  for G4) is written with the accepted trade-offs documented, or the
  run stops with the failing gate named to the user
