# template-customization Specification

## Purpose
The ArcKit template subsystem SHALL provide consistent, template-driven artefact generation with a two-tier template layout (shipped defaults vs user overrides), a regime-routed Document Control header, and a `/arckit:customize` workflow for copying and editing templates.

## Requirements

### Requirement: Two template locations MUST exist with defined precedence
The project template tree SHALL consist of `.arckit/templates/` (shipped defaults, refreshed by `arckit init`) and `.arckit/templates-custom/` (user overrides, preserved across updates). `arckit init` SHALL copy `*.md` templates into `.arckit/templates/` and create `.arckit/templates-custom/` (with an explanatory README) without touching existing files in it. Any command that reads a template SHALL check `.arckit/templates-custom/{name}-template.{ext}` first and fall back to the default only when no custom copy exists.

#### Scenario: arckit init refreshes defaults but preserves customizations
- **WHEN** `arckit init` is run in a project that already contains user-edited files in `.arckit/templates-custom/`
- **THEN** the `.md` templates in `.arckit/templates/` SHALL be re-copied from the installed package or source tree, and the existing files in `.arckit/templates-custom/` SHALL remain untouched

#### Scenario: Custom override takes precedence
- **WHEN** a command (e.g. `/arckit:evaluate`) reads its template and `.arckit/templates-custom/evaluation-criteria-template.md` exists
- **THEN** the command SHALL read the custom file and SHALL NOT read the default; when the custom file is absent, the command SHALL read `${CLAUDE_PLUGIN_ROOT}/templates/evaluation-criteria-template.md` (or the `.arckit/templates/` copy for CLI-scaffolded projects)

### Requirement: Plugin commands MUST reference templates via the plugin root
Plugin commands SHALL reference their templates through the `${CLAUDE_PLUGIN_ROOT}/templates/` prefix (e.g. `${CLAUDE_PLUGIN_ROOT}/templates/requirements-template.md`) so the plugin resolves files in-place at the installed plugin root rather than relying on a copied project tree.

#### Scenario: Command template path uses CLAUDE_PLUGIN_ROOT
- **WHEN** a plugin command under `plugins/arckit-claude/commands/` reads its default template
- **THEN** the path it reads SHALL begin with `${CLAUDE_PLUGIN_ROOT}/templates/`

### Requirement: /arckit:customize MUST list and copy templates
The `/arckit:customize` command SHALL support `list` (list all available templates, covering the core `arckit` plugin and every bundled community overlay under `${CLAUDE_PLUGIN_ROOT}/plugins/**/templates/`, stating the scope and totals) and `<name>` (copy one template for editing). `all` SHALL copy the core templates only and SHALL say so explicitly. When copying a template, the command SHALL update the origin banner from `Template Origin: Official` to `Template Origin: Custom | Based On: /arckit.{command}` and write the result to `.arckit/templates-custom/{name}-template.{ext}`, creating the directory if needed.

#### Scenario: Listing templates
- **WHEN** the user runs `/arckit:customize list`
- **THEN** the command SHALL glob both `${CLAUDE_PLUGIN_ROOT}/templates/*-template.{md,html}` and `${CLAUDE_PLUGIN_ROOT}/plugins/**/templates/*-template.{md,html}`, report totals per scope (core vs overlays, grouped by owning plugin), and render overlay groups from the glob results rather than a hardcoded list

#### Scenario: Copying a template for editing
- **WHEN** the user runs `/arckit:customize requirements`
- **THEN** the command SHALL read `${CLAUDE_PLUGIN_ROOT}/templates/requirements-template.md`, rewrite the origin banner to `Custom | Based On: /arckit:requirements`, and write `.arckit/templates-custom/requirements-template.md`

#### Scenario: Copying an overlay template
- **WHEN** the user requests a template that exists only in a community overlay (e.g. `uae-ai-charter`)
- **THEN** the command SHALL glob `${CLAUDE_PLUGIN_ROOT}/plugins/**/templates/{name}-template.*`, copy the matched file, update the banner as above, and state which overlay plugin the template came from

### Requirement: Every markdown template MUST start with Document Control and Revision History and end with the standard footer
Every `*-template.md` under `plugins/arckit-claude/templates/` SHALL begin with a `## Document Control` section containing the `<!-- DOC-CONTROL-HEADER -->` marker (with a comment noting it is resolved at command-execution time per `_partials/RENDERING.md`) followed by a `## Revision History` table with columns `Version | Date | Author | Changes | Approved By | Approval Date`. The template SHALL close with the standard footer block: `**Generated by**`, `**Generated on**`, `**ArcKit Version**`, `**Project**`, `**Model**`.

#### Scenario: Template head structure
- **WHEN** `plugins/arckit-claude/templates/requirements-template.md` is read
- **THEN** its first section SHALL be `## Document Control` containing the `<!-- DOC-CONTROL-HEADER -->` marker, followed by `## Revision History` with the six standard columns and an initial `[VERSION] / [DATE] / ArcKit AI / Initial creation` row

#### Scenario: Template footer structure
- **WHEN** any markdown template under `plugins/arckit-claude/templates/` is read
- **THEN** its tail SHALL contain the five-line footer `**Generated by**: ArcKit /arckit.{command}` / `**Generated on**` / `**ArcKit Version**` / `**Project**` / `**Model**` (machine-stamped `## Build Provenance` blocks appended by `provenance-stamp.mjs` are not part of the template and SHALL NOT be required in the template source)

### Requirement: Document Control header MUST be resolved from regime-routed partials
When a template contains the `<!-- DOC-CONTROL-HEADER -->` marker, the command that renders the artefact SHALL resolve the marker per `templates/_partials/RENDERING.md`: the doc-type's regime is looked up in the regime index, regimes that hard-route (AT, AU, CA, FR, NL, UAE, US) SHALL select their own partial regardless of user config, regimes that fall through (UK, MOD, EU) and doc-types with no regime SHALL resolve through the user's plugin userConfig (`classification_scheme` / `governance_framework`), landing on `document-control-uk.md` unless a UAE or AT scheme is set. The selected partial's contents SHALL be inlined at the marker with `${user_config.organisation_name}` and `${user_config.default_classification}` substitutions applied, and the marker line SHALL be removed from the final artefact.

#### Scenario: Hard-routed regime beats user config
- **WHEN** a command whose `doc-type:` is a Canadian code (e.g. `FITAA`) renders an artefact in a project whose userConfig says `governance_framework: UK Gov`
- **THEN** the resolved Document Control header SHALL come from `document-control-ca.md` with the Canadian classification ladder, not the UK partial

#### Scenario: Fall-through regime uses user config
- **WHEN** a command whose doc-type regime falls through (e.g. a UK `REQ` artefact) is rendered with `governance_framework: UAE Federal` set in userConfig
- **THEN** the resolved Document Control header SHALL come from `document-control-uae.md`

#### Scenario: Marker is removed from output
- **WHEN** an artefact is written to disk after Document Control resolution
- **THEN** the final artefact SHALL NOT contain the `<!-- DOC-CONTROL-HEADER -->` marker or its descriptive comment

### Requirement: Template changes MUST be made in both source trees
When adding or modifying a template, the change SHALL be applied to both `plugins/arckit-claude/templates/` (the Claude plugin source, referenced in-place via `${CLAUDE_PLUGIN_ROOT}/templates/`) and `.arckit/templates/` (the CLI package-data copy shipped to scaffolded projects and refreshed by `arckit init`).

#### Scenario: New template is duplicated to both trees
- **WHEN** a maintainer adds a new `*-template.md` to `plugins/arckit-claude/templates/`
- **THEN** the same file SHALL also exist at `.arckit/templates/` so that `arckit init` scaffolds it into new projects and CLI-based users get the default
